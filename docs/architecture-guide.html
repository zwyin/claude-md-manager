01 项目概述

01 项目概述

定位与动机

claude-md-manager 是一个模块化管理 ~/.claude/CLAUDE.md 的工具链。Claude Code 使用这个文件作为全局指令——所有会话启动时自动加载。随着规则增多，单文件会膨胀到数千行，难以维护和追踪。

本项目解决三个核心问题：

  1. 可维护性 — 将单一 CLAUDE.md 拆分为 15 个独立的 rule 文件，每个文件带 YAML frontmatter
  2. 可观测性 — 通过 Hook 机制追踪哪些规则被实际引用，并在仪表盘中可视化
  3. 安全性 — Draft/Publish 工作流 + 自动快照，防止误操作破坏全局配置

技术栈

层技术用途
构建系统Python 3.10+ / PyYAML解析 frontmatter、拼接规则、快照管理
数据层SQLite (stdlib + better-sqlite3)引用记录、规则元数据、草稿、发布历史
HookPython (PostToolUse Hook)扫描 JSONL 会话日志，匹配关键词

核心工作流

                                       ↓
Claude Code 会话 → JSONL 日志 → hooks/session-logger.py → SQLite
                                                              ↓
                              Web Dashboard / MCP Server ←──┘
  1. 构建：python build/assemble.py 读取 rules/*.md，按 order 排序拼接为 CLAUDE.md
  2. 追踪：PostToolUse Hook 触发 session-logger.py，扫描会话日志匹配关键词
  3. 可视化：Web 仪表盘读取 SQLite 展示引用热力、冷门规则、趋势图表
  4. 编辑：Web 编辑器或 MCP Server 修改规则 → 保存草稿 → 验证 → 发布

设计特点

  1. 双数据层：Python 后端和 Node.js 前端共享同一个 SQLite 文件，各自维护连接逻辑
  2. 草稿安全网：所有修改通过草稿表暂存，发布前强制快照，失败不清空草稿
  3. 只读/读写分离：Web 仪表盘查询使用 readonly 连接，编辑器使用读写连接

03 构建系统 assemble.py

build/assemble.py（247 行）是整个系统的核心——将 rules/*.md 中的模块化规则文件组装为单一的 ~/.claude/CLAUDE.md。

Frontmatter 解析

def parse_frontmatter(content: str) -> tuple[dict, str]:
    """Parse YAML frontmatter from markdown content."""
    match = re.match(r"^---\n(.*?)\n---\n(.*)", content, re.DOTALL)
    if not match:
        return {}, content
    meta = yaml.safe_load(match.group(1))
    body = match.group(2)
    return meta or {}, body

用正则提取 YAML 块和 Markdown 正文。返回 (metadata_dict, body_string) 元组。

规则加载与排序

def load_rules() -> list[tuple[str, dict, str]]:
    """Load all rule files, sorted by order."""
    rules = []
    for f in sorted(RULES_DIR.glob("*.md")):
        content = f.read_text(encoding="utf-8")
        meta, body = parse_frontmatter(content)
        order = meta.get("order", 999)
        rules.append((f.name, meta, body, order))
    rules.sort(key=lambda x: x[3])
    return [(name, meta, body) for name, meta, body, _ in rules]

先用文件名排序保证稳定性，再按 order 字段重新排序。缺失 order 的规则默认排到末尾。

校验系统

validate_rules() 检查三个维度：

  • id 唯一性：全局去重
  • 子规则 id 前缀：sub_rule.id 必须以 parent_rule.id. 开头
  • 关键词必填：每个子规则至少有一个 keyword

自动 Git Commit

只在输出实际变化时才创建快照和 commit。避免无意义的 git 历史膨胀。

CLI 接口

命令功能
python build/assemble.py构建 + 写入 + 快照 + git commit
--dry-run预览到 stdout
--validate校验所有规则文件格式
--list-snapshots列出可用快照
--rollback <ts>回滚到指定快照

04 数据层 db.py

hooks/db.py（155 行）是 Python 端的 SQLite 数据层。被 session-logger.py 和 mcp_lib.py 共同依赖。

Schema 设计

6 张表、4 个索引：

rule_references    → 引用记录 (rule_id, session_id, matched_keyword, timestamp)
sessions           → 会话信息 (session_id PK, model, task_summary)
rules_metadata     → 规则元数据 (rule_id PK, section_id, title, keywords JSON)
sections_metadata  → 章节元数据 (section_id PK, title, rule_count)
rule_drafts        → 草稿 (rule_id PK, frontmatter_yaml, markdown_body, order_override)
publish_history    → 发布历史 (id AUTO, rules_changed, snapshot_name, status)

连接管理

def get_db() -> sqlite3.Connection:
    DB_PATH.parent.mkdir(parents=True, exist_ok=True)
    conn = sqlite3.connect(str(DB_PATH))
    conn.row_factory = sqlite3.Row
    conn.executescript(SCHEMA_SQL)  # 幂等初始化
    return conn

懒初始化：首次连接时自动创建 schema。Row factory 允许列名访问。调用方负责 conn.close()。

引用记录去重

双重去重策略：应用层 seen set + 数据库层 INSERT OR IGNORE。同一会话中同一规则的同一关键词只记录一次。

05 引用追踪 session-logger.py

hooks/session-logger.py（205 行）是 Claude Code 的 PostToolUse Hook。每次工具调用后自动触发。

触发机制

在 ~/.claude/settings.json 注册：matcher: "" 匹配所有工具调用。

关键词索引

keyword_map 将小写关键词映射到 (rule_id, original_keyword) 对。从 rules/*.md 的 frontmatter 中构建。

会话定位

def find_latest_session() -> Path | None:
    cutoff = time.time() - 3600  # 1 hour ago
    for project_dir in projects_dir.iterdir():
        for jsonl_file in project_dir.glob("*.jsonl"):
            mtime = jsonl_file.stat().st_mtime
            if mtime >= cutoff and mtime > best_mtime:
                best_path = jsonl_file

性能优化：只扫描最近 1 小时内修改的 JSONL 文件。

JSONL 扫描逻辑

  1. 过滤消息类型：只处理 type == "assistant" 的条目
  2. 提取文本：content 可能是 block 数组，提取 type == "text" 的块
  3. 大小写不敏感匹配：kw_lower in content_lower
  4. 去重：同一规则+同一关键词只记一次

已知限制

  • 每次触发扫描整个 JSONL 文件，会话增长后耗时增加
  • 使用子串匹配，不支持正则或语义匹配
  • 只返回单个最新会话，多会话并行可能遗漏

Draft/Publish 安全工作流

两阶段提交保证安全性：

发布流程详解 ▶
  1. Force Snapshot：在任何文件写入之前强制保存当前 CLAUDE.md
  2. Build rule map：扫描 rules/*.md 建立 rule_id → source_file 映射
  3. Write drafts：将每个草稿写入对应的 rule 文件
  4. Run assemble.py：重建 CLAUDE.md
  5. Record history：写入 publish_history 表
  6. Clear drafts：成功才清空草稿表；失败则保留供重试

校验机制

发布前必须校验 YAML frontmatter 中包含三个必填字段：id、title、order。使用正则 re.search(r"^field:", yaml, re.MULTILINE) 检查。

function MiniSparkline({ session, matches }) {
  const max = Math.max(session, matches, 1);
  const h1 = 16 - (session / max) * 12;
  const h2 = 16 - (matches / max) * 12;
  return (
    <svg width="48" height="16" viewBox="0 0 48 16">
      <polygon points={`0,16 12,${h1} 36,${h2} 48,16`} fill={PRIMARY} fillOpacity="0.15" />
      <circle cx="12" cy={h1} r="2" fill={PRIMARY} />
      <circle cx="36" cy={h2} r="2" fill={PRIMARY} />
    </svg>
  );
}

12 设计决策与创新点

5 大创新点

  1. 模块化 CLAUDE.md — 拆分为 15 个独立文件，git diff 友好
  2. Draft/Publish 双阶段提交 — 强制快照 + 确认后才生效
  3. 关键词级引用追踪 — 精确到子规则的关键词粒度
  4. 双界面操作 — MCP Server（CLI）+ Web 编辑器共享草稿状态
  5. 原子化自动 Git Commit — 有变化才 commit，快照+规则一并入库

5 个关键取舍

取舍 1：双数据层 vs 统一 API ▶

选择：两套独立的数据访问层（Python + TypeScript），共享 SQLite。

原因：Python Hook 必须独立运行，Web 端需要 better-sqlite3 同步 API。统一 API 会引入 HTTP 开销，对 Hook 启动时间不可接受。

代价：草稿发布逻辑在 mcp_lib.py 和 editor-db.ts 中各实现一次。

取舍 2：子串匹配 vs 语义匹配 ▶

选择：简单的大小写不敏感子串匹配。

原因：Hook 在每次工具调用后触发，需要极快执行速度。

代价：误报（关键词出现在无关上下文）和漏报（语义匹配但关键词未出现）。

取舍 3：内存 SQLite vs Mock ▶

选择：:memory: SQLite 而非 mock 数据库。

原因：SQL 查询复杂（JOIN、GROUP BY、时间过滤），mock 无法测试真实 SQL 行为。

取舍 4：CodeMirror vs textarea ▶

选择：CodeMirror 6（~200KB 依赖），提供语法高亮。

代价：增加 bundle size，但只在编辑器页面加载（code splitting）。

取舍 5：execFileSync 调用 Python vs Node.js 重写 ▶

选择：Web 端发布时调用 Python 构建脚本。

原因：assemble.py 已有完整实现和测试，重写意味着维护两套。

代价：部署环境必须 Python + Node.js 双栈。
